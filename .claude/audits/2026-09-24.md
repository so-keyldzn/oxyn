### P1 — Prevent AI redirects from bypassing the authorized destination

[Issue #7](https://github.com/so-keyldzn/oxyn/issues/7)

#### Problem

The Reach check applies to base_url before sending. The three HTTP clients keep reqwest's automatic redirects: a 307/308 can resend the prompt to another origin without a new check. A connection at the Local tier can thus leave the machine, while the ai_egress trace keeps the initial reach. Anthropic and Azure also use x-api-key/api-key, which reqwest's removal of sensitive headers does not strip on an origin change.

#### Scenario

An authorized local provider answers 307 or 308 with another origin in Location. The client follows the redirect with the request body. Test with two synthetic servers and a sentinel key, never a real key.

#### Evidence and limits

Static demonstration: Reach check, then independent construction of the transport, no redirect(Policy::none()). Installed source of reqwest 0.13.4 consulted: default policy limited to ten redirects; Authorization removed, but not x-api-key/api-key. No real data transfer performed.

- [crates/oxyn-llm/src/anthropic/mod.rs:146](https://github.com/so-keyldzn/oxyn/blob/27ff313da5b9c488866e276dac6b148348f313c3/crates/oxyn-llm/src/anthropic/mod.rs#L146-L150)

Complete static path confirmed. The existing LLM tests pass (223/223) but do not prove this protection. No real leak caused. Persisting the failure keeps a category: no leak to disk is claimed here.

### P1 — Distinguish a submitted draft from a draft actually saved

[Issue #10](https://github.com/so-keyldzn/oxyn/issues/10)

#### Problem

lastDraft is initialized to the initial text of a new, unpersisted document, then advanced before saveDocument acknowledges. A prefilled copy may never be written; after a write error, flush also considers the text already saved and no longer submits it. The interface can close having lost the ability to recover the last draft.

#### Scenario

1. Create a new console prefilled from History/Saved query, call flush without editing. 2. Edit a draft, make saveDocument fail, restore storage and call flush.

#### Evidence and limits

Two reproductions run in memory on the real hook (React/JSDOM, simulated IPC): case 1 -> zero saveDocument calls; case 2 -> a single call in total despite the next flush. No simulation of a real disk loss.

### P1 — Protect production reads against SQL functions that write

[Issue #11](https://github.com/so-keyldzn/oxyn/issues/11)

#### Problem

The console copies config.read_only independently of the environment. On a writable Production connection, a SELECT calling a mutating function is classified Read and allowed without confirmation. The driver opens a READ ONLY transaction only if limits.read_only is true.

#### Scenario

Precondition: a VOLATILE function allowed to the connected role exists and performs INSERT/UPDATE/DELETE, for example public.audit_touch() inserting a row into a test table. Run SELECT public.audit_touch() from the console on a Production connection not marked read_only. The side effect writes without the confirmation naming the connection.

#### Evidence and limits

Complete static chain confirmed. No PostgreSQL reproduction performed, no real database contacted. The built-in AI path already forces read_only=true on reads; this issue targets the human console. docs/AI-PROVIDERS.md:236-238 acknowledges side effects behind SELECT/view.
