### P1 — Empêcher les redirections IA de contourner la destination autorisée

[Issue #7](https://github.com/so-keyldzn/oxyn/issues/7)

#### Problème

Le contrôle Reach porte sur base_url avant l'envoi. Les trois clients HTTP conservent les redirections automatiques de reqwest : un 307/308 peut retransmettre le prompt à une autre origine sans nouveau contrôle. Une connexion au niveau Local peut ainsi sortir de la machine, tandis que la trace ai_egress conserve la portée initiale. Anthropic et Azure utilisent aussi x-api-key/api-key, que le retrait des en-têtes sensibles de reqwest ne supprime pas lors d'un changement d'origine.

#### Scénario

Un fournisseur local autorisé répond 307 ou 308 avec une autre origine dans Location. Le client suit la redirection avec le corps de la demande. Tester avec deux serveurs synthétiques et une clé sentinelle, jamais une clé réelle.

#### Preuves et limites

Démonstration statique : contrôle Reach puis construction indépendante du transport, absence de redirect(Policy::none()). Source installée de reqwest 0.13.4 consultée : politique par défaut limitée à dix redirections ; retrait de Authorization, mais pas x-api-key/api-key. Aucun transfert de données réelles effectué.

### P1 — Expurger les clés API des erreurs reçues dans un flux SSE

[Issue #8](https://github.com/so-keyldzn/oxyn/issues/8)

#### Scénario

Un serveur synthétique reçoit une clé sentinelle et répond HTTP 200, puis un événement SSE error dont le message répète cette sentinelle. Suivre ChatEvent::Error -> AiError::Provider -> AiUpdate affiché.

#### Preuves et limites

Chemin statique complet confirmé. Les tests LLM existants passent (223/223) mais ne prouvent pas cette protection. Aucune fuite réelle provoquée. La persistance de l'échec conserve une catégorie : aucune fuite sur disque n'est affirmée ici.

### P1 — Respecter Cancel lorsqu'une sauvegarde de fermeture se termine tardivement

[Issue #9](https://github.com/so-keyldzn/oxyn/issues/9)

#### Problème

Cancel retire le dialogue, mais la continuation déjà suspendue sur handle.save() conserve current et appelle finishClose après résolution. Le bouton Cancel est utilisable pendant la sauvegarde : la console peut disparaître après l'annulation explicite.

#### Scénario

Ouvrir une console modifiée, choisir Save and close, retarder la sauvegarde, choisir Cancel, puis résoudre la sauvegarde. L'onglet doit rester ouvert et les éditions ultérieures doivent rester accessibles.

#### Preuves et limites

Reproduction exécutée en mémoire avec React renderHook/JSDOM, code TS réel transpilé et IPC simulé : entriesAfterCancel=1 ; entriesAfterLateSave=0 ; closeCalls=1. Pas de recette de la fenêtre native. Le store refuse la fermeture sans abandon d’un document modifié : aucune perte de modifications ultérieures n’est démontrée par cette reproduction.

Deux reproductions exécutées en mémoire sur le hook réel (React/JSDOM, IPC simulé) : cas 1 -> zéro appel saveDocument ; cas 2 -> un seul appel au total malgré le flush suivant. Pas de simulation de perte disque réelle.

### P1 — Protéger les lectures de production contre les fonctions SQL qui écrivent

[Issue #11](https://github.com/so-keyldzn/oxyn/issues/11)

#### Problème

La console copie config.read_only indépendamment de l'environnement. Sur une connexion Production inscriptible, un SELECT appelant une fonction mutante est classé Read et autorisé sans confirmation. Le driver n'ouvre une transaction READ ONLY que si limits.read_only est vrai.

#### Scénario

Précondition : une fonction VOLATILE autorisée au rôle connecté existe et fait INSERT/UPDATE/DELETE, par exemple public.audit_touch() insérant une ligne dans une table de test. #### Preuves et limites

Chaîne statique complète confirmée. Aucune reproduction PostgreSQL effectuée, aucune base réelle contactée. Le chemin IA intégré impose déjà read_only=true aux lectures ; cette issue vise la console humaine. docs/AI-PROVIDERS.md:236-238 reconnaît les effets de bord derrière SELECT/vue.
